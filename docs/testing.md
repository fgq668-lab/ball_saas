# 场馆预约与球员约战 SaaS 系统测试文档

## 1. 测试目标

测试目标是确保系统在多场馆、多用户并发预约、微信支付、退款、MVP 约战加入退出、P1 约战成局等核心场景下稳定可靠。

重点保障：

- 场地不能重复预约。
- 支付成功后订单状态正确。
- 微信回调重复到达不会重复处理。
- 退款金额和状态正确。
- MVP 约战基础流程正确：发起人基于已支付预约创建约战，成员可加入和退出。
- P1 约战 AA 支付、成局、未成局退款逻辑正确。
- 场馆之间数据隔离。
- 部署不会影响服务器已有产品。

## 2. 测试环境

当前测试服务器：

```text
服务器：1.69.143.156
SSH 端口：2218
用户：frank
限制：没有 80/443 端口
```

测试部署要求：

- API 测试环境使用高位端口，建议 `18200`。
- 管理后台测试环境使用高位端口，建议 `18201`。
- 小程序正式环境不得直接请求 `http://1.69.143.156:18200`，必须通过备案域名和 HTTPS 入口访问。
- 域名申请只是第一步，正式联调前还必须完成备案、HTTPS 证书、小程序合法域名配置和微信支付回调地址配置。
- 当前服务器没有 80/443 时，应验证 `https://api.xxx.com` 可以通过 HTTPS 网关或代理转发到 `http://1.69.143.156:18200`。
- PostgreSQL 和 Redis 不暴露公网。
- 容器名、目录、端口不得与其他产品冲突。
- 部署前后都要检查服务器已有服务状态。

## 3. 测试类型

### 3.1 单元测试

覆盖范围：

- 价格计算
- 退款规则
- 佣金计算
- 订单状态机
- 约战状态机
- 时间冲突判断
- 金额计算

要求：

- 金额用整数分测试。
- 边界时间必须测试。
- 状态流转必须测试非法流转。

### 3.2 接口测试

覆盖范围：

- 登录
- 场馆入驻
- 场馆审核
- 场地管理
- 价格配置
- 可预约时间查询
- 创建预约订单
- 支付单创建
- 支付回调
- 退款申请
- 约战创建
- 加入约战
- 后台订单查询

### 3.3 集成测试

覆盖范围：

- Spring Boot + PostgreSQL
- Spring Boot + Redis
- 预约订单 + 支付回调
- MVP：约战成员加入/退出
- P1：约战 AA 支付
- 退款 + 订单状态
- 定时任务 + 超时订单关闭

### 3.4 并发测试

重点场景：

- 多个用户同时抢同一场地同一时间段。
- 多个用户同时加入同一个约战局。
- 支付回调重复到达。
- 支付成功回调与超时关闭任务并发执行。
- 退款接口重复提交。
- 定时任务和用户支付同时发生。

验收要求：

- 同一场地同一时间段只能成功一个正式预约。
- 约战人数不能超过最大人数。
- 支付单不会重复入账。
- 退款单不会重复退款。

### 3.5 安全测试

覆盖范围：

- 未登录访问后台接口
- 普通用户访问他人订单
- 场馆管理员访问其他场馆数据
- 篡改订单金额
- 篡改场馆 ID
- 伪造支付回调
- 重放支付回调

## 4. 核心测试用例

### 4.1 场馆入驻

用例：

```text
提交完整入驻资料，状态变为待审核
平台审核通过，场馆状态变为审核通过
平台审核驳回，记录驳回原因
停用场馆后，小程序不可预约该场馆
场馆管理员不能访问其他场馆数据
```

### 4.2 场地管理

用例：

```text
新增场地成功
停用场地后不可预约
维护时间不可预约
同一场馆内场地名称可按规则限制重复
不同场馆之间场地数据隔离
```

### 4.3 价格计算

用例：

```text
工作日价格正确
周末价格正确
节假日价格优先级高于工作日
特殊日期价格优先级最高
跨多个时间段时金额累加正确
价格配置为空时不可下单
```

### 4.4 普通预约

用例：

```text
用户选择可用场地并创建待支付订单
创建订单后 Redis 临时锁生效
临时锁有效期内其他用户不能重复下单
支付成功后支付单变为支付成功，预约订单变为已预约
支付超时后订单变为支付超时
支付超时后场地释放
已停用场地不可预约
已过期时间不可预约
```

### 4.5 并发预约

用例：

```text
10 个用户同时预约同一场地同一时间段，只能成功 1 个
10 个用户同时预约不同场地，可以分别成功
60 分钟订单应占用 2 个连续 30 分钟时间槽
90 分钟订单应占用 3 个连续 30 分钟时间槽
支付回调和超时关闭同时发生时，最终状态只能是已预约或支付超时之一
正式时间槽写入失败时，支付单可保持支付成功，但业务订单必须进入待处理或退款流程，不得错误标记为已预约
```

### 4.6 微信支付

用例：

```text
创建支付单时金额与业务订单一致
用户支付成功后正确处理回调
重复支付回调只处理一次
伪造签名回调被拒绝
支付成功后不能修改订单金额
支付成功后不能取消为未支付状态
```

### 4.7 退款

用例：

```text
开场前 24 小时申请全额退款成功
开场前 2 小时申请部分退款成功
不可退款时间内申请退款失败
场馆原因取消时全额退款
重复提交退款只生成一笔有效退款单
微信退款回调重复到达只处理一次
未开始且全额退款成功后释放场地
部分退款、已核销订单退款、已完成订单售后退款不释放场地
```

### 4.8 约战

用例：

```text
用户基于已支付预约订单创建公开约战
用户加入约战成功
同一用户不能重复加入同一约战
达到最大人数后不允许继续加入
成员退出后人数状态正确
P1：成员加入约战并支付成功
P1：达到最低人数后约战变为已成局
P1：未达到最低人数且过截止时间，约战自动取消并退款
```

### 4.9 分账与结算

用例：

```text
订单完成后生成结算记录
佣金比例计算正确
固定服务费计算正确
部分退款后结算金额正确
全额退款后不产生有效分账
分账失败后可重试
```

### 4.10 权限与数据隔离

用例：

```text
平台管理员可查看全部场馆订单
场馆管理员只能查看自己场馆订单
场馆员工只能核销自己场馆订单
普通用户只能查看自己的订单
修改请求中的 venue_id 不能越权访问数据
```

## 6. 联调测试

微信支付联调前置条件：

- 小程序 AppID
- 已备案 API 域名，例如 `api.xxx.com`
- HTTPS 证书，建议可通过 DNS 校验申请
- 小程序后台已配置 request 合法域名
- 微信支付服务商商户号，正式推荐方案需要
- 场馆特约商户号，正式推荐方案需要
- 平台普通商户号，MVP 过渡方案可使用
- API v3 密钥
- 商户证书
- 支付回调地址，必须是公网 HTTPS
- 退款回调地址，必须是公网 HTTPS

注意：

- 当前服务器没有 443 端口，正式微信支付回调通常需要公网 HTTPS 地址。
- 如果当前服务器无法提供 HTTPS 回调，需要使用可用 HTTPS 的网关、隧道、云函数、API 网关或其他服务器转发。
- 本地和测试环境可以先使用模拟支付回调验证业务流程。

## 8. 验收标准

MVP 验收必须满足：

- 平台可以新增并审核场馆。
- 场馆可以配置场地和价格。
- 用户可以在小程序查询可预约场地。
- 用户可以创建预约订单。
- 同一场地同一时间不会被重复预约。
- 支付成功后支付单变为支付成功，预约订单变为已预约。
- 支持原路退款。
- 用户可以基于已支付预约创建约战。
- 用户可以加入约战。
- 约战人数满后状态正确。
- P1：用户可以加入约战并支付。
- P1：未成局约战能自动取消并退款。
- 场馆后台只能看到自己的数据。
- 平台后台能查看全局订单和结算。
- 部署在 `1.69.143.156` 时不影响已有产品。
